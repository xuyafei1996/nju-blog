> **设计原则**：一切皆 ChartConfig。预设模板、AI 对话、异常预警、分享链接——四个入口产出同一份 JSON，走同一条渲染管道。这就是"不臃肿"的秘诀。

## 一、产品愿景与用户

### 1.1 一句话定位

**让产品经理用自然语言问数据，系统自动分析并呈现可视化结果。**

### 1.2 目标用户

| 角色 | 痛点 | 使用方式 |
|------|------|----------|
| 产品经理 | 不懂 SQL，不会配置分析参数，每次分析都找开发 | 自然语言对话，AI 翻译意图 |
| 运营 | 需要定期看数据，但每次都重复同样的操作 | 固定看板 + 一键导出报告 |
| 研发负责人 | 需要快速了解产品数据全貌 | 预设看板，一页概览 |
| 老板 | 只关心结论，不关心过程 | 分享链接 / 静态报告 |

### 1.3 用户故事

| 编号 | 故事 | 优先级 |
|------|------|--------|
| US-1 | 作为产品经理，我打开页面就能看到常用指标，不需要每次手动配置 | P0 |
| US-2 | 作为产品经理，我可以用大白话描述需求（"上周各渠道的访问量对比"），系统帮我生成图表 | P0 |
| US-3 | 作为产品经理，AI 生成的分析参数我可以在确认前修改，防止理解偏差 | P0 |
| US-4 | 作为产品经理，我可以把 AI 对话中生成的图表"钉"到看板上，下次打开还在 | P1 |
| US-5 | 作为运营，我每天早上收到企微消息，告诉我昨天数据有没有异常 | P1 |
| US-6 | 作为运营，我可以把分析结论一键导出为 HTML 报告发给老板 | P1 |
| US-7 | 作为产品经理，我可以把分析结果分享链接发给同事，对方打开就能看到同样的图表 | P2 |
| US-8 | 作为产品经理，我可以继续上次的分析会话，而不是从头开始 | P2 |

## 二、核心设计：一切皆 ChartConfig

### 2.1 数据结构

整个系统的唯一流通数据格式：

```json
{
  "id": "uuid",
  "title": "首页浏览 → 按钮点击 转化漏斗",
  "chartType": "funnel",
  "apiEndpoint": "/analytics/funnel",
  "apiParams": {
    "steps": ["page_view", "click_btn"],
    "startTime": "2026-09-01 00:00:00",
    "endTime": "2026-09-30 23:59:59",
    "windowMinutes": 30
  },
  "options": {
    "showTable": true,
    "height": 400
  },
  "source": "preset",
  "createdAt": "2026-09-03T10:00:00"
}
```

### 2.2 图表类型枚举

| 类型 | 说明 | 对应 API |
|------|------|----------|
| `funnel` | 漏斗图，展示逐步转化率 | `/analytics/funnel` |
| `trend` | 趋势折线图，按天展示变化 | `/analytics/range-times-count` / `range-people-count` |
| `bar` | 柱状图，维度对比排名 | `/analytics/dimension` |
| `pie` | 饼图，占比分布 | `/analytics/dimension` |
| `table` | 数据表格，支持排序和分页 | 任意 API |
| `retention` | 留存热力图，N 日留存矩阵 | `/analytics/retention` |
| `metric_card` | 指标卡，大数字 + 环比变化 | `/analytics/times-count` + `people-count` |

### 2.3 四入口 → 一管道

```
┌──────────────┐
│ 预设模板 (L1) │──┐
├──────────────┤  │
│ AI 对话 (L2)  │──┼──→ ChartConfig ──→ ChartRenderer ──→ 图表
├──────────────┤  │
│ 异常预警 (L3) │──┤
├──────────────┤  │
│ 分享链接 (L4) │──┘
└──────────────┘
```

**关键设计决策**：ChartRenderer 不关心 ChartConfig 的来源。无论它是预设的、AI 生成的、还是告警触发的，渲染逻辑完全相同。这是整个系统不臃肿的根本原因。

## 四、交互流程

### 4.1 预设看板流程（L1）

```
打开页面
    │
    ├── 首次访问 → 空状态 → 点击 [加载预设看板]
    │                              │
    └── 回访用户 → 加载上次保存的布局 ←──┘
                        │
                        ▼
              渲染 6 个预设图表（并排显示）
              （每个图表独立加载，loading 状态独立）
                        │
                        ▼
              用户可拖拽排序、删除、刷新单个图表
              用户可点击 [添加图表] 从预设库中选择更多
              布局自动保存到 localStorage
```

### 4.2 AI 对话流程（L2）

```
用户在对话面板输入自然语言
    │  例："帮我看看 9 月首页各渠道的访问量"
    ▼
前端发送 POST /ai/chat { message: "..." }
    │
    ▼
后端调用 LLM API 解析意图
    │  System Prompt: 你是一个数据分析助手，可用 API 有...
    │  LLM 返回：{ intent, apiEndpoint, apiParams, confirmMessage }
    │
    ▼
后端风控检查
    │  · 时间范围 ≤ 90 天？
    │  · API 在白名单中？
    │  · 参数值合法？
    │  · 频率限制？
    │
    ├── 不通过 → 返回错误提示，前端展示修改建议
    │
    └── 通过 → 返回 AiChatResult (ChartConfig + confirmMessage)
                    │
                    ▼
            前端展示参数确认卡片
                    │
            ┌───────┼───────┐
            │       │       │
        [确认]  [修改]   [取消]
            │       │       │
            ▼       ▼       ▼
    POST /ai/execute  修改参数后  放弃本次查询
    { chartConfig }   重新确认
            │
            ▼
    后端调用对应的分析 API，返回数据
            │
            ▼
    前端在对话中内联渲染图表
            │
            ├── [📌 固定到看板] → 添加到右侧 DashboardGrid
            ├── [🔗 分享] → 生成分享链接
            └── [📥 导出] → 导出 PNG/HTML
```

### 4.3 异常预警流程（L3）

```
定时任务（每天 9:00 触发）
    │
    ▼
后端遍历所有监控规则
    │  每条规则 = ChartConfig + 阈值 + 对比窗口
    │
    ▼
执行每条规则的 ChartConfig，获取当日数据
    │
    ▼
计算 当日值 vs 过去 N 天均值
    │
    ├── 正常 → 跳过
    │
    └── 超过阈值 → 生成告警记录
            │
            ├── 存入数据库（前端轮询展示）
            │
            └── 推送企微消息
                  │
                  ▼
            企微机器人消息格式：
            ┌──────────────────────────────┐
            │ ⚠️ 数据异常预警               │
            │                              │
            │ page_view 日访问量            │
            │ 昨日：850 次                  │
            │ 近 7 日均值：1,200 次          │
            │ 下降：29.2%                   │
            │                              │
            │ 建议：查看渠道是否有异常       │
            │                              │
            │ [查看详情] ← 跳转到分析页面    │
            └──────────────────────────────┘
```

### 4.4 分享与导出流程（L4）

```
用户点击 [🔗 分享]
    │
    ▼
前端发送 POST /analytics/report/share
    { chartConfig, data }
    │
    ▼
后端生成唯一 share_token，存入 MySQL
    │
    ▼
返回分享链接：/analytics/report/abc123
    │
    ▼
用户复制链接发给同事
    │
    ▼
同事打开链接 → 只读报告页
    · 展示图表 + 数据表格
    · 无 AI 功能，无编辑功能
    · 底部显示：生成时间 | 过期时间（7 天）
    · 支持导出为 HTML / PNG

═════════════════════════════════

用户点击 [📥 导出]
    │
    ├── 导出看板 → 所有图表打包为一个 HTML 文件
    │     · 内联 CSS + ECharts base64 截图
    │     · 包含数据表格
    │     · 不依赖外部资源，可离线打开
    │
    └── 导出单个图表 → PNG 图片（html2canvas 截图）
```

## 六、LLM 集成策略

### 6.1 设计原则

**接口隔离，灵活替换**。通过 `LlmService` 接口解耦，当前使用外部大模型 API Key 方式，后续可无缝切换到 FastGPT 或其他模型。

```
┌──────────────────────┐
│  AiAnalysisService   │  ← 业务层，不关心 LLM 具体实现
└──────────┬───────────┘
           │ 依赖接口
┌──────────▼───────────┐
│  LlmService 接口      │  ← chat(String message, List<Message> history) → LlmResult
└──────────┬───────────┘
           │
     ┌─────┴─────┐
     │           │
┌────▼─────┐ ┌───▼──────┐
│OpenAiImpl│ │FastGptImpl│  ← 各自实现，通过配置切换
│(API Key) │ │(内网API)  │
└──────────┘ └──────────┘
```

### 6.2 配置项（Nacos / application.yml）

```yaml
analytics:
  llm:
    provider: openai           # openai / fastgpt / custom

### 6.3 System Prompt 设计

```
你是一个埋点数据分析助手。你可以使用以下 API 查询数据：

## 可用 API

### funnel - 漏斗分析
用途：分析用户按顺序完成多个步骤的转化率
参数：
  - steps: string[]（必填，事件名数组，按顺序）
  - startTime: string（必填，格式 yyyy-MM-dd HH:mm:ss）
  - endTime: string（必填，格式 yyyy-MM-dd HH:mm:ss）
  - windowMinutes: int（可选，步骤间时间窗口分钟数，默认 30）

### retention - 留存分析
用途：计算 N 日留存率
参数：
  - initialEvent: string（必填，初始事件名）
  - returnEvent: string（必填，回访事件名）
  - startDate: string（必填，格式 yyyy-MM-dd）
  - retentionDays: int[]（必填，留存天数列表，如 [1,3,7,14,30]）

### dimension - 维度聚合
用途：按任意维度组合分组统计
参数：
  - event: string（必填，事件名）
  - startTime: string（必填，格式 yyyy-MM-dd HH:mm:ss）
  - endTime: string（必填，格式 yyyy-MM-dd HH:mm:ss）
  - groupByFields: string[]（必填，分组字段列表）
    可用字段：event, env, channelSource, channelApp, channelCode, sourcePage, sourceFeature
  - metric: "count" | "people"（可选，默认 count）
  - filters: object（可选，额外筛选条件，如 {"channelSource": "web"}）

### times-count - 查询总次数
参数：eventNameEn, startTime, endTime

### people-count - 查询总人数
参数：eventNameEn, startTime, endTime

### range-times-count - 按天统计次数
参数：eventNameEn, startTime, endTime

### range-people-count - 按天统计人数
参数：eventNameEn, startTime, endTime

### monthly-stats - 月度统计
参数：month（格式 yyyy-MM）

## 输出格式

你必须返回合法的 JSON，格式如下：
{
  "intent": "dimension_analysis",
  "chartType": "pie|bar|trend|funnel|retention|table|metric_card",
  "apiEndpoint": "/analytics/xxx",
  "apiParams": { ... },
  "title": "图表标题（简短描述）",
  "confirmMessage": "用中文向用户确认：你理解他要查询什么，列出了哪些参数"
}

## 规则

1. 时间格式必须是 yyyy-MM-dd HH:mm:ss
2. 如果用户没有指定时间范围，默认为最近 7 天
3. 如果用户没有指定事件名，尽可能从上下文推断（如"首页"→page_view）
4. 如果用户没有指定图表类型，根据数据特征推荐：
   - 按时间统计 → trend（折线图）
   - 维度对比 → bar（柱状图）
   - 占比分布 → pie（饼图）
   - 转化分析 → funnel（漏斗图）
   - 留存分析 → retention（热力图）
5. 如果用户说的不够明确，在 confirmMessage 中追问
6. chartType 的推荐在 confirmMessage 中说明，让用户确认

## 七、风控策略

### 7.1 拦截规则

| 层级 | 规则 | 触发条件 | 处理 |
|------|------|----------|------|
| 时间范围 | 最大跨度 90 天 | startTime ~ endTime > 90 天 | 拒绝，提示缩小范围 |
| 时间范围 | 必须包含起止时间 | 缺少 startTime 或 endTime | 默认最近 7 天 |
| API 白名单 | 仅允许调用 8 个分析 API | LLM 返回了非白名单 API | 拒绝，记录日志 |
| 参数白名单 | groupByFields 仅允许 7 个字段 | 字段不在白名单 | 拒绝，提示可用字段 |
| 参数白名单 | metric 仅允许 count/people | 其他值 | 拒绝，提示可用指标 |
| 频率限制 | 同一用户 1 分钟 10 次 | 超限 | 拒绝，提示稍后重试 |
| 敏感数据 | distinct_id 精确查询 | 检测到精确用户查询 | 二次确认弹窗 |

### 7.2 写入操作隔离

**AI 对话路由只暴露查询 API**。写入接口（`/analytics/report`、`/analytics/reportBatch`）不在 AI 可用 API 列表中，LLM 无法生成写入请求。即使 LLM 被 prompt injection 攻击，后端 API 白名单也会拦截。

## 十一、风险与缓解

| 风险 | 概率 | 影响 | 缓解 |
|------|------|------|------|
| LLM 解析不准确，生成错误的 ChartConfig | 中 | 中 | 强制展示参数确认卡片，用户可修改 |
| LLM 响应慢（>5s），用户体验差 | 中 | 高 | 后续加 SSE 流式返回；当前先设 15s 超时 + loading 动画 |
| 用户不知道怎么用 AI 对话 | 高 | 中 | 提供示例问题引导；4.1 预设看板作为保底方案 |
| 外部 LLM API 不稳定 | 低 | 高 | 预设看板不依赖 LLM，可独立使用 |
| 图表数据量大导致渲染卡顿 | 低 | 低 | ECharts 原生支持大数据量；表格分页 |
